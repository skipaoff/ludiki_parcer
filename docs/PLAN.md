# Terminal Ludik — план реализации

> Статус: этапы 0–7 реализованы. Остались шаги, которые требуют ключей и делает владелец: проверка ключей, пробная сделка, живые сценарии торговли, живой тест MVP (раздел 14).
> Дата: 13.09.2026. Платформа: Windows 11 (план изначально писался под macOS, отличия собраны в разделе 4.6).
> Основа: парсер crypto_pars; его модули лежат в `reference/crypto_pars/`.

Локальный торговый терминал межбиржевого ценового гэпа на бессрочных фьючерсах. По сути это свой арбитражный терминал: только для себя, локально и под себя. Вилки появляются в ленте, открываются одной кнопкой, открытые пары мониторятся в реальном времени и закрываются одной кнопкой. Вся история вилок и сделок пишется в базу для статистики.

## 1. Зафиксированные решения

| Тема | Решение |
|---|---|
| Биржи на старте | Binance (фьючерсы USDⓈ-M) и MEXC (фьючерсы). Остальные подключаются по одной после MVP |
| Стратегия сейчас | Только ценовой гэп между биржами, это самое прибыльное |
| Будущие разделы | Фандинг и Разлоки. Заложены в архитектуру, базу и интерфейс, пока заглушки |
| Тип ордеров | Всегда рыночные, и на вход, и на выход |
| Как считаем ROI | По стакану на заданный размер (средняя цена исполнения), а не по last или mark цене. Комиссии тейкера за вход и выход вычитаются |
| Количество | На обеих ногах строго одинаковое количество **токенов**, не долларов |
| Пороги | ROI и все пороги вилок задаются в % разницы цен |
| Размер позиции | Задаётся в настройках торговли. Единица уточняется, см. [раздел 19](#19-открытые-вопросы); пока заложены $ на ногу |
| Плечо | Отдельно для каждой биржи, в настройках торговли |
| Режим позиций | Только one-way (одна позиция в одном направлении на символ) на обеих биржах |
| База данных | PostgreSQL 18 с TimescaleDB |
| Открытие | Быстрый режим: одна кнопка, без окна подтверждения |
| Мониторинг | Реальное время: стаканы обновляются каждые 100–200 мс, интерфейс 4–5 раз в секунду. Минимально допустимое требование — раз в 30 секунд, но этого мало |
| Запуск | Всё работает локально на ноутбуке с Windows 11, ключи не покидают машину |
| Рыночные данные и торговля | Публичные потоки (лучшие цены, стаканы, mark и index) — свои клиенты вебсокетов. Торговля, баланс, позиции и приватные потоки — через ccxt |
| Размер позиции | $ на ногу, пересчёт в одинаковое количество токенов |
| Пробная сделка | На этапе 1: минимальная позиция открывается и сразу закрывается на обеих биржах, до постройки ленты |
| Стиль | Минимализм, чёрно-белый. Цвет только для аварий |
| История | Записываются все вилки, открытые и неоткрытые, со всеми сделками и ордерами |

## 2. Рамки: что входит в MVP и что нет

**Входит в MVP:**
- биржи Binance и MEXC, ключи, проверка подключения;
- лента вилок с ROI по стакану, фильтрами и сортировкой;
- открытие пары одной кнопкой с одинаковым количеством токенов;
- мониторинг открытых пар: спред выхода, PnL при закрытии сейчас, расстояние до ликвидации;
- кнопки «Закрыть пару» и «Закрыть всё»;
- запись всей истории в базу и базовый экран статистики;
- вкладки «Фандинг» и «Разлоки» как заглушки.

**Не входит в MVP, идёт после:**
- автозакрытие по условиям и уведомления;
- другие биржи;
- разделы фандинга и разлоков;
- бэктесты и автооткрытие;
- сервер рядом с биржами.

## 3. Финальная версия: разделы и экраны

### 3.1 Главный экран «Гэпы»

> С 15.09.2026 колонки ленты другие — см. раздел 14, «Экран трейдера и фандинг». Схема ниже — исходный замысел.

```
 ГЭПЫ  Фандинг·скоро  Разлоки·скоро  Сделки  Статистика  Настройки      ● BINANCE 38мс  ● MEXC 61мс
────────────────────────────────────────────────────────────┬────────────────────────────────────────
 ROI ≥ 0.50  ≤ 15.00   Объём 24ч ≥ $1M  ≤ —   □ подозрит.   │ ОТКРЫТЫЕ ПАРЫ  2/3     [ЗАКРЫТЬ ВСЁ]
 Размер $1000 · Binance x3 · MEXC x3          сорт: ROI ↓   │
────────────────────────────────────────────────────────────│ SOL   L MEXC 142.10   S BINANCE 143.05
 МОНЕТА  ЛОНГ            ШОРТ             ROI   ЁМК.  ЖИВЁТ │ 12.40 SOL   вход 0.67% → выход 0.21%
 XYZ     MEXC 1.0040     BINANCE 1.0180   1.19% $3.4K  0:42 │ PnL сейчас +$3.20   до ликв. 18%
                                                  [ОТКРЫТЬ] │ 14:02 в сделке             [ЗАКРЫТЬ]
 ABC     BINANCE 0.3121  MEXC 0.3162      0.94% $9.1K  3:10 │
                                                  [ОТКРЫТЬ] │ ABC   L BINANCE 0.3121  S MEXC 0.3162
 DEF     MEXC 12.402     BINANCE 12.511   0.61% $1.2K  0:05 │ ...
                                                  [ОТКРЫТЬ] │
────────────────────────────────────────────────────────────┴────────────────────────────────────────
 журнал: 14:21:07 ABC открыта · BINANCE 212мс · MEXC 348мс · ROI ожид. 0.94% факт 0.88%
```

**Лента вилок, слева.**

Колонки:
- **Монета.**
- **Лонг:** биржа и средняя цена покупки по стакану на заданный размер.
- **Шорт:** биржа и средняя цена продажи по стакану на заданный размер.
- **ROI:** чистый, после комиссий на вход и выход. ROI до комиссий виден при наведении.
- **Ёмкость:** максимальный объём в $ на ногу, при котором ROI по стакану не ниже порога входа.
- **Живёт:** сколько вилка уже существует.
- **[ОТКРЫТЬ].**

Сортировка по ROI по убыванию. По клику на заголовок можно сортировать по ёмкости или по времени жизни.

Состояния строки:

| Состояние | Вид | Кнопка |
|---|---|---|
| Норма | чёрный текст | активна |
| Устаревшие данные: нога старше порога свежести | серый текст | неактивна, при наведении видна причина |
| Подозрительная пара: расходятся индексные цены | серый текст с пометкой `?`. По умолчанию скрыта | неактивна |
| Блокировка: нет маржи, API биржи недоступно, лимит пар, монета в чёрном списке | серый текст | неактивна, при наведении видна причина |
| Пара уже открыта по этой монете | пометка `●` | неактивна (без усреднения в MVP) |

**Открытые пары, справа.**

В карточке пары:
- монета, биржи и средние цены входа по ногам, количество токенов;
- спред входа (фактический) и спред выхода сейчас (по стакану на объём позиции);
- PnL при закрытии сейчас в $, с комиссиями и фандингом;
- расстояние до ликвидации по худшей ноге;
- время в сделке;
- кнопка [ЗАКРЫТЬ].

Над списком: счётчик «открыто/лимит» и кнопка [ЗАКРЫТЬ ВСЁ].

Статусы карточки:
- `открывается`;
- `открыта`;
- `закрывается`;
- `нога потеряна` — единственный красный элемент интерфейса;
- `нет данных`.

**Шапка.** Вкладки и индикаторы бирж: точка связи и пинг. Если связь потеряна, точка становится полым кругом, а надпись мигает.

**Журнал, нижняя строка.** Последние события: открытия, закрытия, задержки ордеров, ошибки. По клику раскрывается полный журнал.

### 3.2 «Сделки»

История закрытых пар, по одной строке на пару:
- дата и время;
- монета, биржи, количество;
- ROI входа: ожидаемый и фактический;
- спред выхода: ожидаемый и фактический;
- комиссии и фандинг;
- PnL в $ и %;
- время в сделке и причина закрытия.

Фильтры: период, монета, пара бирж, стратегия. Экспорт в CSV.

### 3.3 «Статистика»

**Воронка:**
- вилок обнаружено → попало в ленту → открыто;
- доля открытых по диапазонам ROI.

**Качество исполнения:**
- ожидаемый ROI против фактического (реальное проскальзывание): среднее, медиана, по биржам;
- задержка от клика до исполнения по биржам.

**Результат:**
- PnL за день, неделю, месяц;
- PnL по монетам, по парам бирж, по часам суток;
- доля прибыльных пар, средняя длительность сделки.

**Рынок:**
- сколько живут вилки в каждом диапазоне ROI;
- как часто и за сколько сходятся цены;
- **упущенная прибыль:** сколько принесли бы неоткрытые вилки, если открыть при обнаружении и закрыть в лучший момент.

### 3.4 «Настройки»

Четыре раздела: Биржи и ключи, Торговля, Фильтры, Уведомления. Полный список полей в [разделе 13](#13-настройки-полный-список).

### 3.5 «Фандинг» и «Разлоки» (заглушки)

Вкладки есть, внутри надпись «скоро». В коде у них уже есть свои модули-заглушки, в базе поле `strategy` принимает значения `funding` и `unlocks`. Когда разделы появятся, они будут пользоваться тем же исполнением, портфелем, базой и статистикой.

### 3.6 Визуальный стиль

- **Фон и текст:** фон чёрный (#000), основной текст белый, второстепенный серый (#8a8a8a), линии тёмно-серые.
- **Шрифт:** один моноширинный для цифр и таблиц, например JetBrains Mono или IBM Plex Mono. Все числа выровнены по правому краю.
- **Знак PnL:** без цвета, передаётся знаком `+` или `−` и жирностью.
- **Красный цвет:** только аварии. Это потерянная нога, отказ ордера и обрыв связи при открытых позициях.
- **Без украшений:** нет теней, скруглений, иконок-декораций и анимаций, кроме индикатора связи.

## 4. Архитектура

### 4.1 Слои

| Слой | Ответственность |
|---|---|
| **Адаптеры бирж** | Единый интерфейс: параметры контрактов, потоки рынка (лучшие цены, стакан, mark и index), приватные потоки (позиции, ордера, баланс), отправка и статус ордеров, плечо и режим маржи, комиссии, история фандинга. Публичные потоки — свои клиенты вебсокетов: ccxt отдаёт стаканы во float и собирает стакан Binance из diff-потока с REST-снимками, а нам нужны `depth20@100ms`, точные метки времени и Decimal. Торговля и приватная часть — ccxt |
| **Рыночное ядро** | Стаканы в памяти, контроль свежести данных, радар по всем общим парам, выбор кандидатов для подписки на стакан |
| **Инструменты** | Сопоставление монет между биржами, множители, общий шаг количества в токенах, минимумы и максимумы, флаг подозрительности |
| **Стратегии** | Модуль `price_gap` сейчас, `funding` и `unlocks` заглушками. Выдают вилки в общем формате: стратегия, ноги, метрики, состояние |
| **Исполнение** | Прогрев, проверки перед отправкой, расчёт количества, параллельная отправка, обработка сбоя ноги, закрытие, «Закрыть всё», риск-лимиты. Общее для всех стратегий |
| **Портфель** | Сверка с реальными позициями на биржах, склейка ног в пары, PnL, ликвидации, восстановление после перезапуска |
| **Запись** | Асинхронная очередь пакетной записи в базу, торговый цикл не ждёт диск |
| **API-сервер** | FastAPI: REST для настроек и истории, один WebSocket до браузера со снимками состояния 4–5 раз в секунду и событиями |
| **Интерфейс** | Одна страница в браузере на `127.0.0.1` |
| **Секреты** | Диспетчер учётных данных Windows |

### 4.2 Потоки данных

```
Binance WS ─┐                                   ┌─> Лента (стратегия price_gap) ─┐
MEXC WS ────┼─> Адаптеры ─> Рыночное ядро ──────┤                                ├─> API-сервер ─WS─> Браузер
REST ───────┘      │         (стаканы, радар)   └─> Портфель (открытые пары) ────┘         │
                   │                                     ▲                                 │ клик
                   │                                     │                                 ▼
                   └──────────── приватные потоки ───────┘            Исполнение <── API-сервер
                                                                            │
                          Запись (очередь) <── вилки, семплы, ордера, события
                                │
                            PostgreSQL + TimescaleDB
```

### 4.3 Процессы

**MVP:** один процесс Python на asyncio. На Windows — proactor-цикл: uvloop на Windows не работает, а на selector-цикле asyncpg терял хвост пакетной записи без ошибки (раздел 4.6). На Linux и macOS — uvloop, если установлен. Внутри независимые задачи: адаптеры, ядро, стратегия, исполнение, портфель, запись, сервер.

**Потом, если упрёмся в процессор:** рыночные данные и исполнение разносятся по отдельным процессам.

### 4.4 Стек

| Часть | Выбор |
|---|---|
| Язык | Python 3.13 (поддерживается 3.12+), asyncio, orjson; окружение и зависимости — uv с `uv.lock` |
| Биржи | ccxt 4.5.x: REST и вебсокеты в одном бесплатном пакете. Проверено на версии 4.5.78, Binance USDⓈ-M и MEXC поддерживаются |
| Сервер | FastAPI, uvicorn |
| База | PostgreSQL 18 с TimescaleDB 2.30, asyncpg. Миграции — свой раннер нумерованных SQL-файлов `db/NNN_*.sql` (`app/storage/migrations.py`): те же файлы гоняет CI через psql, ORM нет, а Alembic лишь обернул бы SQL в Python. Обоснование базы в разделе 11.1 |
| Секреты | `keyring`, работает через Диспетчер учётных данных Windows |
| Интерфейс | TypeScript, React и Vite, виртуализированная таблица. Без UI-китов, свой минимальный CSS, шрифт JetBrains Mono лежит локально. Node.js 24 нужен только для сборки, собранный интерфейс отдаёт FastAPI |
| Тесты | pytest, pytest-asyncio; CI на Ubuntu и Windows |
| Запуск | `ludik.cmd`: ставит зависимости и собирает интерфейс при первом запуске, поднимает локальный PostgreSQL, сервер и открывает браузер. Пока есть открытые пары, Windows не засыпает (`SetThreadExecutionState`) |

## 5. Рыночные данные и скорость

### 5.1 Три уровня

| Уровень | Что | Binance | MEXC | Частота |
|---|---|---|---|---|
| 1. Радар | лучшие bid и ask по всем общим парам | поток `<symbol>@bookTicker` по каждой паре, соединения по 200 потоков, плюс досев из REST раз в 30 с для тихих контрактов. Общий `!bookTicker` не подходит: он обновляется раз в 5 секунд | опрос REST `GET /api/v1/contract/ticker` раз в секунду, поля `bid1` и `ask1`. Вебсокет `sub.tickers` лучших цен не содержит, а `maxBidPrice`/`minAskPrice` — ценовые лимиты (см. `docs/EXCHANGES.md`) | Binance в реальном времени, MEXC раз в секунду |
| 2. Стакан кандидатов | стакан для расчёта ROI на размер | `<symbol>@depth20@100ms` | `sub.depth.full` с `limit=20` по паре, по 30 пар на соединение | 100 мс / около 500 мс |
| 3. Открытые пары | стаканы обеих ног постоянно и приватные потоки | стакан, user data stream (позиции, ордера, баланс) | стакан, `push.personal.position`, `.order`, `.asset` | 100–200 мс, приватные потоки мгновенно |

**Вспомогательные данные:**

| Данные | Binance | MEXC |
|---|---|---|
| mark и index цены | `!markPrice@arr@1s` | index и fair цены из `sub.tickers` |
| объём 24ч | REST раз в минуту | `amount24` из `sub.tickers` |
| параметры контрактов | REST при старте и раз в час | REST при старте и раз в час |
| комиссии аккаунта | REST при старте и раз в сутки | REST при старте и раз в сутки |

### 5.2 Кто становится кандидатом

ROI по лучшим ценам всегда не ниже ROI по стакану на любой размер. Поэтому пара, у которой ROI по лучшим ценам (уже после комиссий) ниже порога ленты, точно не даст вилку, и её можно не подписывать на стакан. Отбор без потерь.

Подписки на стакан ограничены лимитом, по умолчанию 60 пар. Приоритет:
1. открытые пары;
2. вилки в ленте;
3. вилки, которые ещё отслеживаются до схождения цен;
4. новые кандидаты по убыванию ROI.

### 5.3 Свежесть данных

- **Возраст ноги:** для каждой ноги хранится время последнего обновления стакана по часам биржи и по локальным часам.
- **Порог свежести:** 1000 мс. Если нога старше, строка серая, а кнопка «Открыть» заблокирована.
- **Тихий стакан:** биржи присылают стакан только при изменении. Нога без изменений дольше порога свежести считается свежей, если её соединение за последние 1000 мс присылало любые кадры, и не дольше 10 с (`core/radar.py::leg_fresh`).
- **Стакана нет 5 с после подписки или он молчит дольше 10 с:** стакан переподписывается.
- **Устаревшие данные по открытой паре** дают статус `нет данных`, в карточке показывается возраст.

### 5.4 Соединения

- **Обрывы:** переподключение с нарастающей паузой. Binance плановo рвёт соединения раз в сутки, это обычная ситуация.
- **Разрыв версий у MEXC:** стакан `sub.depth` приходит изменениями с номером версии. Если номер пропущен, стакан пересобирается.
- **Часы:** расхождение с серверным временем бирж меряется при старте и раз в 10 минут. Это нужно для подписи запросов и для возраста данных.
- **Пинг:** REST-пинг и задержка вебсокета раз в 10 секунд. Показывается в шапке и пишется в базу.

## 6. Сопоставление инструментов

### 6.1 Каноническая монета

Каждый контракт приводится к паре «монета и множитель»:
- Binance `1000PEPEUSDT`: монета `PEPE`, множитель 1000 (одна единица контракта равна 1000 PEPE);
- MEXC `PEPE_USDT`: монета `PEPE`, множитель 1, размер контракта берётся из параметров биржи.

Множитель определяется по префиксу (`1000`, `10000`, `1000000`, `1M`, `k`) и подтверждается сверкой цен: отношение цен должно быть близко к множителю.

Все расчёты ведутся в **реальных токенах** и в цене **за один токен**.

### 6.2 Общий шаг количества

- **Шаг Binance в токенах** = `stepSize` × множитель.
- **Шаг MEXC в токенах** = размер контракта × минимальный шаг объёма в контрактах.
- **Общий шаг** = наименьшее общее кратное двух шагов, считается в десятичной арифметике без float.

Количество для ордера всегда кратно общему шагу. Поэтому на обеих биржах оно без остатка переводится в единицы биржи.

**Ограничения, которые проверяются:**
- минимальное количество и минимальная сумма ордера на каждой бирже;
- максимальное количество для рыночного ордера: у Binance это отдельный фильтр `MARKET_LOT_SIZE`, у MEXC `maxVol`;
- если общий шаг больше заданного размера, пара помечается «размер слишком мал» и не торгуется.

### 6.3 Подозрительные пары

Проверка по индексным ценам. Индекс собирается биржей со спотовых рынков, у одной и той же монеты индексы на двух биржах почти совпадают.

- **Индексы расходятся меньше чем на 1%, а цены фьючерсов разошлись:** это настоящая вилка.
- **Индексы расходятся больше чем на 1%:** скорее всего, это разные токены под одним тикером или сломанный индекс. Пара помечается подозрительной и по умолчанию скрыта.
- **Индекса нет:** пара подозрительная, пока её не подтвердят вручную.

**Ручные списки:** чёрный список монет и отметка «проверено вручную», которая снимает флаг подозрительности.

## 7. Расчёты: ROI, ёмкость, выход, PnL

Все формулы — чистые функции в `app/core/`, у каждой есть unit-тесты.

### 7.1 Средняя цена по стакану

Проход по уровням стакана до набора нужного количества токенов Q:

```
VWAP(стакан, Q) = Σ(цена_i × объём_i) / Q,   где объёмы берутся по уровням, пока их сумма не дойдёт до Q
```

Если глубины стакана не хватает на Q, результат «глубины не хватает», и ROI не считается.

У MEXC объём уровня приходит в контрактах и переводится в токены: объём × размер контракта.

### 7.2 ROI входа

Лонг на бирже L (покупаем по ask), шорт на бирже S (продаём по bid):

```
Q          = floor_to_step(Размер$ / ask_L_лучший, общий_шаг)
ask_L      = VWAP(asks_L, Q)
bid_S      = VWAP(bids_S, Q)
ROI_gross  = (bid_S − ask_L) / ask_L × 100
fees       = (taker_L + taker_S) × 2            # вход и выход на обеих ногах, в %
ROI_net    = ROI_gross − fees
```

**Пример.** Размер $1000. MEXC: средний ask 1.0040. Binance: средний bid 1.0180. Комиссии тейкера 0,05% и 0,05%.
- ROI_gross = (1.0180 − 1.0040) / 1.0040 = 1,394%
- fees = (0,05 + 0,05) × 2 = 0,20%
- **ROI_net = 1,19%**

Направление выбирается автоматически: лонг там, где дешевле. Если дешевле на другой бирже, считается зеркально.

### 7.3 Ёмкость

Максимальный размер в $ на ногу, при котором ROI_net не ниже порога входа. Ищется бинарным поиском по количеству в пределах видимой глубины (20 уровней).

### 7.4 Спред выхода и PnL при закрытии сейчас

Закрытие: продаём лонг на L по bid, выкупаем шорт на S по ask. Q_pos — реальное количество позиции.

```
bid_L_exit   = VWAP(bids_L, Q_pos)
ask_S_exit   = VWAP(asks_S, Q_pos)
exit_spread  = (ask_S_exit − bid_L_exit) / bid_L_exit × 100

PnL_now$ = Q_pos × (bid_L_exit − entry_L)
         + Q_pos × (entry_S − ask_S_exit)
         − комиссии_входа_факт
         − комиссии_выхода_оценка
         + фандинг_получен − фандинг_уплачен
```

Грубо: итог ≈ спред входа − спред выхода − комиссии. В карточке это видно как «вход 0.67% → выход 0.21%».

### 7.5 Расстояние до ликвидации

```
до_ликв_% = |mark − цена_ликвидации| / mark × 100
```

Считается по каждой ноге отдельно, в карточке показывается худшая. Цена ликвидации берётся из позиции на бирже.

Ноги на разных биржах, общей маржи у них нет. Лонг может ликвидировать при резком падении, даже если шорт на другой бирже в плюсе. Предупреждение при расстоянии меньше 10%, по умолчанию.

## 8. Лента вилок и жизненный цикл вилки

### 8.1 Состояния вилки (эпизода)

```
кандидат ──> вилка в ленте ──> вышла из ленты ──> сходится ──> завершена
                  │                                               ▲
                  └──── открыта (есть сделка) ────────────────────┘
```

| Переход | Условие (значения по умолчанию, меняются в настройках) |
|---|---|
| кандидат → в ленте | ROI_net по стакану ≥ мин. ROI ленты, и вилка живёт не меньше **45 с** (решение владельца 14.09.2026: секундные рывки руками не поймать). **Исключение с 21.09.2026:** вилке выше **4× порога** (при пороге 0,50 % — от 2 %) хватает **5 с**. Ожидание доказывает, что вилку успеешь кликнуть, а не что она настоящая: подлинность проверяют сходимость индексов, глубина стакана и объём слабой ноги. Крупная вилка — и самая ценная, и самая быстросходящаяся, держать её 45 с значит терять её. Провалы ниже мин. ROI − 0,10 п.п. короче 2 с отсчёт не сбрасывают, более долгий провал или потеря данных — сбрасывают. Быстрый путь выключается `fast_enter_multiple = 0` и никогда не делает ожидание длиннее обычного |
| в ленте → вышла | ROI_net < мин. ROI − 0,10 п.п. дольше 2 с (гистерезис) |
| вышла → сходится | вилка продолжает отслеживаться: пишется спред выхода |
| сходится → завершена | цены сошлись (спред выхода ≤ 0), или прошло 24 ч, или делистинг, или вытеснена из лимита подписок, или остановлен терминал |
| открыта | нажата кнопка. Эпизод связывается со сделкой и отслеживается до закрытия сделки |

**Упущенная прибыль.** Для каждой завершённой вилки считается гипотетический результат: вход при появлении в ленте, выход в лучший момент до завершения, с комиссиями. Так видно, что было оставлено на столе и какой порог ROI реально оправдан.

### 8.2 Фильтры ленты

- ROI мин. и ROI макс. Максимум отсекает фейки.
- Объём 24ч мин. и макс., **по слабой ноге**: берётся меньший объём из двух бирж. В парсере бралось максимальное значение, это исправлено.
- Ёмкость мин. в $.
- Показывать подозрительные: да или нет (по умолчанию нет).
- Биржа лонга и биржа шорта (понадобится, когда бирж станет больше).
- Поиск по монете.

**Сортировка:** ROI (по умолчанию), ёмкость, время жизни, объём.

## 9. Исполнение: открытие и закрытие

### 9.1 Прогрев

Как только пара попала в ленту, в фоне по обеим биржам:
- выставляется плечо из настроек, отдельно для Binance и для MEXC;
- выставляется режим маржи: изолированная или кросс;
- проверяется режим позиций. Терминал работает только в one-way на обеих биржах. Если на бирже включён hedge, торговля по ней заблокирована, а в Настройках → Биржи висит предупреждение с инструкцией, как переключить режим.

Результат кешируется, повторно на ту же пару не выставляется. Если прогрев не удался, кнопка заблокирована с причиной. Поэтому в момент клика уходят только сами ордера.

### 9.2 Клик «Открыть»

**1. Проверки перед отправкой.** Идут по данным в памяти и занимают миллисекунды:
- обе ноги свежее порога свежести;
- ROI_net по текущему стакану не ниже порога входа (порог задаётся в настройках);
- количество кратно общему шагу и укладывается в минимумы и максимумы обеих бирж;
- на каждой бирже хватает свободной маржи: размер / плечо плюс запас;
- риск-лимиты не превышены: число открытых пар, общий объём, одна пара на монету;
- торговое API обеих бирж доступно, последних отказов «на обслуживании» нет;
- прогрев выполнен.

**2. Отправка.**
- Два рыночных ордера уходят одновременно, у каждого свой `clientOrderId`, связанный с id сделки.
- У Binance ордер отправляется через уже открытый торговый вебсокет, если это стабильно; иначе через REST с постоянным соединением.
- У MEXC ордер отправляется через REST с постоянным соединением.

**3. Подтверждение.** Исполнения приходят по приватным потокам. Если за 2 секунды подтверждения нет, статус ордера запрашивается по `clientOrderId`.

**4. Запись в базу:**
- ROI, ожидавшийся в момент клика;
- фактические средние цены и фактический ROI;
- задержки: клик → отправка → ответ биржи → исполнение, по каждой ноге;
- снимок настроек.

### 9.3 Сбой ноги

| Ситуация | Действие терминала |
|---|---|
| Обе ноги исполнены полностью | пара `открыта` |
| Одна нога отклонена, другая исполнена | исполненная нога сразу закрывается рыночным reduce-only ордером. Сделка получает статус `сбой ноги`, красная плашка, событие в журнал |
| Одна нога исполнена частично | большая нога уменьшается reduce-only до размера меньшей, пара открывается на меньшем количестве. Если меньшее количество ниже минимумов, закрываются обе |
| Ответа от биржи нет, исполнение неизвестно | запрос статуса по `clientOrderId` и позиции. До выяснения пара в статусе `открывается`, кнопки по монете заблокированы, красная плашка. После выяснения — одно из действий выше |
| Ошибка сети при отправке одной ноги | то же, что «отклонена» |

Поведение по умолчанию: **закрыть исполненную ногу**. Голая нога без присмотра не остаётся никогда.

### 9.4 Закрытие пары

1. Количество по каждой ноге берётся из **реальной позиции** на бирже, а не из базы.
2. Два рыночных reduce-only ордера уходят одновременно.
3. Если одна нога не закрылась, три повтора с паузой 300 мс. Дальше статус `нога потеряна`, красная плашка и кнопка «Закрыть ногу» по отдельной бирже.
4. После закрытия подтягиваются фактические комиссии и фандинг за время сделки, PnL фиксируется в базе.

**«Закрыть всё»** закрывает все открытые пары параллельно по той же схеме.

### 9.5 Риск-лимиты

Стартовые значения, все меняются в настройках:

| Лимит | По умолчанию |
|---|---|
| Максимум открытых пар | 3 |
| Максимальный общий объём по всем парам | $5 000 на ногу суммарно |
| Одна пара на монету | да |
| Минимальный запас свободной маржи после входа | 20% |

## 10. Портфель и мониторинг открытых пар

**Склейка ног.** Позиции с обеих бирж склеиваются в пары по id сделки из базы.

**Сверка с биржами:**
- по приватным потокам — постоянно;
- через REST — раз в 30 секунд, как страховка.

**Расхождения при сверке:**

| Ситуация | Статус и действие |
|---|---|
| Позиция есть на бирже, но её нет в базе | «чужая позиция»: показывается, но терминал ей не управляет |
| Нога есть в базе, но её нет на бирже (закрыли руками или ликвидировало) | статус `нога потеряна`, в журнал пишется причина из истории ордеров |
| Количество не совпадает | предупреждение и кнопка «Выровнять» |

**Перезапуск терминала.** При старте позиции с бирж сверяются с базой, пары восстанавливаются, стаканы переподписываются.

**Пока есть открытые пары:**
- Windows не засыпает (`SetThreadExecutionState`, `app/system/keep_awake.py`);

## 11. База данных

### 11.1 Выбор

**Решение (13.09.2026):** PostgreSQL 18 с расширением TimescaleDB.

**Почему не SQLite.** Главный объём базы — временные ряды: семплы вилок раз в секунду, снимки радара, семплы открытых пар. Это миллионы строк в сутки, а по плану они копятся месяцами. На этом объёме:
- **сжатие:** TimescaleDB сжимает старые данные в разы, SQLite хранит всё как есть;
- **агрегаты для статистики:** минутные и дневные сводки пересчитываются в фоне. В SQLite каждый отчёт сканировал бы сырые таблицы;
- **чтение во время записи:** экран статистики и сверка портфеля читают базу, пока идёт запись, и не мешают ей. У SQLite один писатель на весь файл;
- **переезд на сервер:** если терминал переедет на сервер или появится второй пользователь, база переносится как есть.

**Цена решения:** нужен PostgreSQL и расширение TimescaleDB. На Windows это архив бинарников PostgreSQL 18.6 от EDB и официальная сборка TimescaleDB 2.30.0 под PostgreSQL 18 для Windows, обе распакованы в `ludik-data/pgsql`. Кластер `ludik-data/pgdata` слушает только `127.0.0.1`, вход по scram-sha-256, пароль в Диспетчере учётных данных, телеметрия TimescaleDB выключена. Службы Windows нет: терминал запускает кластер через `pg_ctl`, если он не запущен, и не останавливает его при выходе.

**Проверка.** CI на GitHub прогоняет `db/001_schema.sql` и `db/002_timescale.sql` на образе `timescale/timescaledb:2.30.0-pg18` при каждом пуше.

**Страховка.** Запись идёт через слой `storage/`, так что при необходимости базу можно заменить без переписывания терминала.

### 11.4 Запись

- Все записи идут через асинхронную очередь (`app/storage/writer.py`), пакетами раз в 300 мс.
- Торговый цикл никогда не ждёт базу.
- Если база недоступна, очередь буферизуется в памяти и на диск (`ludik-data/spool/*.jsonl`, не реже раза в 5 с), потом дописывается в исходном порядке раньше новых строк. Торговля продолжается, в шапке появляется предупреждение.
- Пока писать нечего, очередь раз в 5 с проверяет связь с базой, чтобы обрыв был виден сразу.
- Строки, которые база отвергла (ошибка данных, а не связи), откладываются в `rejected-*.jsonl` и не блокируют остальные.
- Миграции применяются при подключении: каждый файл `db/NNN_*.sql` один раз, с контрольной суммой. Изменённый после применения файл останавливает подключение — изменения идут только новым номером.

## 12. Ключи и безопасность

**Хранение:**
- Ключи хранятся только в Диспетчере учётных данных Windows через `keyring`. Их нет в файлах, в базе, в логах, в git и в ответах API до браузера.
- Логи проходят маскировку: каждое значение, прочитанное из хранилища ключей, и поля вида `apiKey`, `signature`, `X-MBX-APIKEY`, `listenKey` заменяются на `***`.
- В интерфейсе ключ показывается замаскированным (`abcd…wxyz`). Его можно заменить или удалить, но не посмотреть.

**Требования к ключам на бирже:**
- только чтение и торговля фьючерсами, **вывод выключен**;
- Binance: терминал проверяет права ключа через API и не принимает ключ с включённым выводом;
- MEXC: права проверяются через API, если биржа их отдаёт; иначе в настройках висит предупреждение с инструкцией. Для торговли фьючерсами через API на MEXC нужна пройденная KYC;
- привязка к IP желательна. У части бирж ключи без привязки к IP ограничены по сроку, это проверяется на этапе 1.

**Сеть:**
- Сервер слушает только `127.0.0.1`, другой адрес в настройках не принимается.
- Браузер подключается с токеном сессии. Терминал открывает страницу с токеном во фрагменте URL (`#t=`): фрагмент не уходит на сервер, страница сразу убирает его из адресной строки и держит в `sessionStorage`. REST получает токен в заголовке `Authorization`, WebSocket — первым сообщением, поэтому в логи он не попадает.
- Токен создаётся при первом запуске и лежит в Диспетчере учётных данных. Перезапуск терминала его не меняет, поэтому открытые вкладки переподключаются сами; повторный запуск `ludik.cmd` при работающем терминале открывает его с тем же токеном. `ludik.cmd --new-session` выпускает новый токен.
- Проверяются заголовки `Host` (только `127.0.0.1`, `localhost`, `[::1]`) и `Origin` у WebSocket. Чужой сайт в браузере не сможет обратиться к терминалу, в том числе через DNS rebinding.

**Логи:** подписи, ключи и полные заголовки запросов не пишутся.

## 15. Тестирование

**Unit-тесты чистого ядра** (`tests/core`):

- ROI и ёмкость: зеркальное направление, комиссии, граничные значения;

- разбор стакана;
- разбор позиций;
- разбор исполнений и ошибок.

Новая биржа подключается, только когда проходит весь набор.

## 16. Масштабирование после MVP

Порядок предварительный, уточняется по итогам живого теста.

1. **Автозакрытие и уведомления:**
   - условия закрытия: спред выхода достиг цели, PnL ≥ $X, стоп по убытку, максимальное время в сделке, угроза ликвидации;
   - звук и сообщения в свой Telegram.
2. **Новые биржи по одной:** Bybit, OKX, Bitget, потом Hyperliquid и Aster. Все есть в ccxt, каждый адаптер проходит контрактные тесты. **Gate подключена 14.09.2026, Variational — только на чтение** (подробности ниже и в `docs/EXCHANGES.md`).
   - Лента превращается в матрицу всех пар бирж.
   - Появляется фильтр по биржам.
   - Hyperliquid работает не по API-ключу, а через API-кошелёк без права вывода.
3. **Балансы:** панель балансов по биржам с подсказками, где не хватает маржи. Перевод средств остаётся ручным, ключи без права вывода.
4. **Фандинг:**
   - сначала колонка стоимости удержания в ленте гэпов: разница ставок фандинга по ногам за 8 часов;
   - потом отдельный раздел фандинг-арбитража на основе `funding_sources.py` из парсера.
5. **Разлоки:** раздел календаря разлоков на основе `token_unlocks.py` с фильтром по наличию фьючерсов на подключённых биржах.
6. **Аналитика:**
   - бэктест порогов и фильтров на накопленных вилках и снимках радара;
   - симуляция «что если»;
   - опционально автооткрытие по правилам, по умолчанию выключено, включается только после подтверждения цифрами.
7. **Производительность:**
   - рыночные данные и исполнение в отдельных процессах;
   - при необходимости сервер рядом с биржами. Это отдельное решение, потому что ключи тогда покидают локальную машину.

## 17. Риски и как их закрываем

| Риск | Защита |
|---|---|
| Одна нога открылась, другая нет | параллельная отправка, `clientOrderId`, таблица решений 9.3, закрытие исполненной ноги по умолчанию, красная плашка |
| Проскальзывание между проверкой и исполнением рыночного ордера | ROI считается по стакану на весь размер, фильтр ёмкости, порог свежести 1 с. Фактическое проскальзывание пишется в базу, по нему калибруется порог входа |
| Фейковый гэп: разные токены под одним тикером, множители | индексные цены, подтверждение множителя по ценам, ROI макс., чёрный список, отметка «проверено» |
| Ликвидация одной ноги при резком движении | изолированная маржа, умеренное плечо по умолчанию, предупреждение о ликвидации, позже автозакрытие по угрозе ликвидации |
| Ноутбук уснул, перезагрузился из-за Windows Update или пропал интернет при открытых парах | запрет сна через `SetThreadExecutionState`, настройка питания и «часов активности» Windows, предупреждение при закрытии терминала, сверка и восстановление при старте. Позиции на биржах остаются, пока терминал недоступен, — это надо помнить |
| Тихая потеря строк при записи в базу | proactor-цикл на Windows, пакетная запись одним запросом со сверкой числа строк, проверка каталога после записи, интеграционные тесты записи |
| Антивирус перехватывает HTTPS к биржам | исключения для доменов бирж в Avast до этапа 1; без них — лишняя задержка, обрывы вебсокетов и заголовки с API-ключом в руках перехватчика |
| Торговое API биржи на обслуживании | ошибки «на обслуживании» блокируют кнопку по этой бирже и пишутся в журнал |
| Устаревшие данные выглядят как вилка | контроль свежести по каждой ноге, переподписка, серые строки |
| Гэп держится из-за перекоса фандинга и съедает прибыль | фандинг учитывается в PnL с MVP, колонка стоимости удержания — первым делом после MVP |
| Утечка ключей | Диспетчер учётных данных Windows, вывод выключен, только `127.0.0.1`, токен сессии, проверка Host и Origin, маскировка секретов в логах |
| Python не справляется с потоком стаканов | уровни и лимит подписок, замер на этапе 3, при необходимости разнос по процессам |

- цены сделок `lastPrice` вместо стакана;

- выбрасывание пар с множителем (`1000PEPE`);

- Telegram-логику и хранение подписчиков.
